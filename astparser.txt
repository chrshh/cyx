⏺ Congrats, that's real progress. Let me give you the mental model that will
  save you from this class of problem going forward.

  ---
  Your current problem in one sentence

  Your Command struct is trying to be both a description of structure and a set
  of execution hints (isEnv, etc.). When a new case appears, you add another
  flag, and the flags start fighting each other.

  ---
  The core insight of an AST

  The parser's only job is to answer: what is this grammatically? The executor's
   only job is to answer: given what this is, what do I do?

  Right now parseEq is deciding "this is an env assignment" — that's an
  execution decision leaking into parsing. The problem you just hit (echo 
  PATH=...) is a direct consequence.

  ---
  What your node types should look like

  You don't need a complex AST. For a shell at your stage, you need roughly
  three things:

  1. SimpleCommand — a command word plus a list of argument words. echo foo bar
  is one of these.
  2. Assignment — a name and a value. PATH=foo with no preceding command is one
  of these.
  3. Pipeline — a list of SimpleCommands connected by pipes.

  The key distinction: PATH=foo and echo PATH=foo are different node types, not
  the same node with a different flag. The parser decides which one at the
  statement level by looking at whether there's a command word before the =.

  ---
  How argument words work (this is what you're really missing)

  Right now args are char ** — flat strings. But $PATH:/path/to isn't a flat
  string, it's a concatenation of a variable expansion and a literal. You need
  words to be composed:

  Word = Literal("PATH=")
       | VarExpansion("PATH")
       | Concat([Literal("PATH="), VarExpansion("PATH"), Literal(":/path/to")])

  The executor walks a word and builds the final string. This is why shells
  handle foo$BAR$BAZ correctly — each piece is a node, assembled at execution
  time.

  ---
  What the executor becomes

  A simple switch on node type:

  - SimpleCommand → fork/exec (or check builtins)
  - Assignment → setenv
  - Pipeline → connect pipes, run each SimpleCommand

  No flags. No isEnv. The structure tells you everything.

  ---
  Practical path forward

  You don't have to rewrite everything at once. The highest-leverage change is:

  1. Make the parser decide Assignment vs SimpleCommand at the top level (before
   it recurses into tokens), based on whether the pattern is WORD = ... with
  nothing before it
  2. Represent args as a list of "word parts" rather than flat strings, so
  concatenation and expansion happen cleanly in one place

  The rest of your current structure can stay. You're closer than you think —
  you basically have an implicit AST already, you just need to make the node
  types explicit so the executor doesn't need flags to figure out what it's
  looking at.

⏺ Take a simpler example: the shell input

  echo "hello $USER!"

  In your current approach, the lexer probably produces something like a STRING
  token with the literal hello $USER!, and you have to figure out inside that
  string where the variable is. That's the same problem you just fought.

  With word parts, the parser breaks that string into a list before it becomes
  an arg:

  [ Literal("hello "), VarExpansion("USER"), Literal("!") ]

  The executor walks that list, expands each piece, and concatenates the results
   into one final string: hello christopher!. No special casing needed anywhere.

  Now take $HOME/.config/foo:

  [ VarExpansion("HOME"), Literal("/.config/foo") ]

  Or "prefix_${VAR}_suffix":

  [ Literal("prefix_"), VarExpansion("VAR"), Literal("_suffix") ]

  In every case the executor does the same thing — loop over the parts, build a
  string. It never needs to scan a flat string looking for $ signs. The
  lexer/parser already found all the boundaries.

  The reason this matters for you specifically: right now expansion logic is
  scattered across parseEq, parseVar, expandVarInStr — each handling a slightly
  different context. With word parts, there is one place that says "given a list
   of parts, produce a string", and every command arg, every assignment value,
  every here-string goes through the same function.

⏺ Neither the command binary nor the executor strips it — the parser is
  responsible, and it does it by recognizing two completely different
  grammatical structures before any execution happens.

  ---
  export PATH="$PATH:/path/to"

  The parser sees: keyword export, then PATH=.... It recognizes this whole thing
   as an AssignmentStatement with a name PATH and a value word-parts list. The =
   is a grammatical delimiter — it tells the parser where the name ends and the
  value begins. It never becomes an arg. The executor gets a clean {name: 
  "PATH", value: [VarExpansion("PATH"), Literal(":/path/to")]} and calls setenv.

  ---
  echo PATH="$PATH:/path/to"

  The parser sees: command word echo, then PATH=.... Because echo is not a known
   assignment keyword, PATH=... is treated as a regular argument word. The =
  here is just a character inside a word, not a delimiter. The word parts become
   [Literal("PATH="), VarExpansion("PATH"), Literal(":/path/to")]. The executor
  gets a SimpleCommand with that as one arg, expands it to the string
  PATH=/actual/value, and passes it to echo. Echo prints it.

  ---
  The key: the parser makes the decision based on position and context, not on
  what the binary does or doesn't want. export triggers "I am parsing an
  assignment statement." A regular word triggers "I am parsing command
  arguments, and = is just a character." The binary never sees the = question at
   all — by the time exec happens, the structure is already decided.

⏺ In a POSIX shell the special ones are:

  Assignment-like keywords — where = is a delimiter, not a character:
  - export NAME=value
  - local NAME=value (inside functions)
  - readonly NAME=value
  - declare NAME=value / typeset NAME=value

  Bare assignment — no command at all:
  - NAME=value (just sets the variable in the current shell)

  That's the = family. Everything else — echo, grep, find, anything you'd think
  of — treats = as a plain character.

  ---
  The rule that covers all of them is actually simple: if the thing before = is 
  a valid identifier and it appears at the start of a statement, it's an 
  assignment context. The parser only needs to know a small list of keywords
  (export, local, readonly, declare) to know that = is a delimiter when it
  follows them too.

  ---
  There are a few other tokens with similar "means different things depending on
   context" behavior you'll hit as you go:

  - > and >> — redirection after a command, but just a character inside a word
  - | — pipe between commands, but || is a logical OR
  - & — background execution, but && is logical AND
  - ( — subshell or command grouping
  - ~ — home dir expansion, but only at the start of a word

  Each one has a small finite set of contexts where it's special. The parser
  just needs to know those contexts. It's not an infinite problem — POSIX shells
   have been doing this with the same finite list for 40 years.

❯ Something i dont know is how do i know when a variable has ended in           
  expandWord? For example i know PATH is the full variable but how do i         
  communicate that in code when people can set their own variables?             

⏺ By the time expandWord runs, that question is already answered.

  expandWord receives a WordPart * list. Someone else — parseWord — already
  figured out where the variable name starts and ends and put just the name in
  value. So when expandWord sees a WP_VAR node it just calls getenv(part->value)
   on whatever string is sitting there. No scanning needed.

  The scanning question is parseWord's problem. And there the answer is simpler
  than you'd think — variable names can only contain letters, digits, and
  underscores. So when parseWord sees a $ it reads forward consuming characters
  while they're alphanumeric or _, and stops the moment it hits anything else —
  a /, :, ", space, $, end of string, whatever. Everything it consumed is the
  variable name.

  So $PATH:/path/to breaks down as: hit $, read forward — P, A, T, H, then hit :
   which is not alphanumeric or _, so the variable name is PATH, stop. Emit
  WP_VAR("PATH"), then continue from : and emit WP_LITERAL(":/path/to").

  That rule — alphanumeric plus underscore — is exactly what POSIX defines for
  variable names. It's also why ${PATH} syntax exists, for cases like
  ${VAR}suffix where the braces tell the parser unambiguously where the name
  ends. You don't need to handle that yet but that's the reason it exists.

❯ i see you keep saying emit but what does that mean?                           

⏺ It just means "create a node and add it to the list."

  When I say "emit WP_VAR("PATH")" I mean call makeWordPart(WP_VAR, "PATH") and

  "Emit" is just jargon borrowed from compilers where the lexer "emits tokens"
  as it scans. Same idea — you found a thing, now produce the data structure
  that represents it. I'll stop using it.
